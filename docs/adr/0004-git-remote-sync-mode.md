# Git Remote Sync Mode — a second Sync Folder transport alongside the plain-folder one

**Context**: ADR 0001's bare-remote-folder design (a plain folder mirrored by an external tool — Syncthing, OneDrive, Google Drive) needed real fixes, documented in that ADR's 2026-08-22 updates, to a ref-overwrite race, incomplete SAF directory listings, and the merge silently dropping changes it never received. All three trace back to the same root cause: a general-purpose file-sync tool doesn't understand git, so it touches git's internal files (loose objects, refs) at the byte level, with no concept of atomic ref updates or complete object negotiation. Syncthing's own response to two devices editing that shared ref file — renaming one into a `.sync-conflict-*` copy — is the same root cause from a different angle: it's not a Syncthing bug, it's what any file-sync tool does when it can't merge something it doesn't understand.

**Decision**: Add a second Sync Folder transport, **Git Remote mode**, that reaches a real git server (GitHub, GitLab, or self-hosted — from isomorphic-git's side, all three are just "a URL plus credentials") over git's actual smart-HTTP push/fetch protocol. No file-sync tool is in the loop at all in this mode: the server itself owns atomic ref updates (a non-fast-forward push is rejected server-side — real compare-and-swap, not the manifest-based approximation folder mode needs against a dumb file store) and always knows its own true object set (no directory-listing truncation is possible — the server either has an object or it doesn't, and says so).

**Folder mode stays the default and is not going away** — existing installs need zero migration, and it's still the right choice for someone who doesn't want to run or pay for a git server. Git Remote mode is opt-in, chosen explicitly per device in Account → Folder Sync (or noted as available during first-run setup).

**Implementation**:
- `gitRemoteTransport.ts` wraps isomorphic-git's `fetch()`/`push()`/`getRemoteInfo()`. Fetches into the *same* `DEFAULT_REMOTE_TRACKING_REF_NAME` (`refs/remotes/sync-folder/main`) that folder mode's hand-rolled pull already uses — achieved by passing `remote: 'sync-folder'` — so `mergeBridge.ts`'s merge logic needs zero branching by sync mode; only how the tracking ref gets populated differs.
- `gitSync.ts`'s `syncNowInternal()` branches once, at the top, on the configured mode; the merge-application logic (`applyMergeIfNeeded()`) is shared between both branches.
- `syncSettings.ts` centralizes the mode flag, git-remote config (URL/username/token/optional CORS proxy), and the new configurable auto-sync interval — all via Capacitor Preferences, the same plain on-device storage every other setting in this app already uses. The token is flagged in the settings UI as not being a secret-store value (this isn't a shared-database credential like the server-mode cloud LLM keys, which are encrypted specifically because Postgres is shared; this token lives only on the device that typed it in).

**Considered options**: fixing folder mode's bugs and stopping there (rejected — the bugs are inherent to a file-sync tool touching git internals, not implementation mistakes on top of a sound design; no amount of patching removes the file-sync tool from the loop); replacing folder mode entirely with git-remote mode (rejected — forces every user to stand up a git server just to sync between their own devices, a real cost folder mode doesn't have).

**Consequences**: Device-record tracking (folder mode's "Known Devices" list) isn't implemented for Git Remote mode yet — there's no equivalent of "drop a file next to the git dir" for a real remote, only commit+push, and committing purely to refresh a last-synced timestamp every cycle would spam the history for no real benefit; revisit if this turns out to matter (e.g. by deriving it from commit-log authorship instead of a separate file).

**Update (2026-08-22)**: the first shipped version routed requests through `isomorphic-git/http/web`, which runs them through the WebView's own `fetch()` — subject to the browser's CORS policy, and GitHub/GitLab's git-smart-HTTP endpoints don't send CORS headers (built for native git clients, not browser JS), so every request from this app got blocked before reaching application code (`Failed to fetch`, no useful detail). The originally-planned mitigation was isomorphic-git's own `corsProxy` option, defaulting to the public `cors.isomorphic-git.org` proxy — tested live and found to be actively rejecting requests (Cloudflare bot-challenge page, HTTP 403), i.e. a real single point of failure outside this project's control, not a hypothetical one.

Fixed properly instead of patched around: this app already has a way to escape the WebView's sandbox entirely for exactly this class of problem — `electronFs()`/`gitfs.ts` bridge filesystem calls to Electron's main process over IPC, and `SafMirror` bridges Android's folder access to a native Capacitor plugin, specifically because CORS/sandbox restrictions that apply to *web content* don't apply to native app code at all (it's a browser policy, not a network-layer one). `nativeHttpClient.ts` does the same for HTTP: Electron's `smartchef-http-request` IPC handler runs the request via Node's `fetch()` in the main process; Android's `GitHttpPlugin.java` (a new Capacitor plugin, registered alongside `SafMirrorPlugin`) runs it via `HttpURLConnection`. Neither is subject to CORS, so both reach GitHub/GitLab/self-hosted servers directly — no proxy, public or self-hosted, needed at all. The `corsProxy` field stays in the settings UI as a rarely-needed escape hatch (isomorphic-git still honors it as a URL rewrite ahead of the `HttpClient` call if a user sets one for some other reason) but is no longer required, or even suggested, for the common case.

**Update (2026-08-22, second finding)**: a second device (a desktop with a large pre-existing local library, syncing after Android had already pushed once) hit `git.push()` throwing `PushRejectedError: not a simple fast-forward` on every single attempt — not an edge case, but the permanent, universal case for every device except whichever one happened to push first. Root cause: `applyMergeIfNeeded()` (shared with folder mode, see `gitSync.ts`) reconciles content field-by-field via Structured Merge and commits the result with a single parent — this device's own previous commit — never a real two-parent git merge commit linking back into the remote's history it just fetched. From git's own ancestry-checking perspective that's indistinguishable from two branches that diverged and were never merged, so isomorphic-git's client-side fast-forward check refuses every time, regardless of how fresh the preceding fetch+merge was.

Folder mode never hits this because `pushObjectsAndRefs()` (`gitObjectTransport.ts`) writes the ref as raw bytes, never going through git's own push machinery or its ancestry check at all — its safety instead comes from the manifest/compare-and-swap check against the exact ref bytes last observed. Fixed by passing `force: true` to `git.push()` in `pushGitRemote()`: this only skips isomorphic-git's own local pre-flight ancestry check, not safety itself — the actual safety (pushing content that was just computed FROM the remote's current state, per the pull-before-push ordering both sync modes share) was already there, just not expressed in a form git's ancestry check could recognize. Skipping a check that can't recognize an equivalent guarantee already being upheld is not the same as removing the guarantee.
