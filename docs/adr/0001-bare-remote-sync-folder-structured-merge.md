# Bare-remote Sync Folder with Structured Merge for standalone-mode storage

**Context**: Standalone-mode devices previously shared a single folder that served as both the live git working copy and the thing an external tool (OneDrive/Drive/Syncthing) replicated — coupling live-database integrity to external replication timing, and relying on last-write-wins reconciliation with no real conflict detection.

**Decision**: Local Storage (the live database/images) and the Sync Folder (a separate, externally-replicated location) are now distinct. Each device drives its own Hidden Clone against the Sync Folder as a bare-style git remote using real fetch/push, and merges using Structured Merge (field-level JSON comparison against a common ancestor) rather than git's textual merge — genuine conflicts are surfaced to the user instead of being silently resolved.

**Considered options**: keeping the single-folder mirror model (rejected — couples live data to external replication); git's native textual merge (rejected — a text-level conflict can leave unparseable conflict markers inside a JSON entity file); silent last-write-wins for all conflicts (rejected — risks silently losing a user's edit without their knowledge).

**Consequences**: The Android `SafMirror` native plugin is retained as the low-level SAF file-access layer, but the byte-mirror algorithm built on top of it is replaced entirely. Full history at [issue #4](https://github.com/MGriot/smartchef/issues/4).

**Update (2026-08-20)**: "using real fetch/push" above is conceptually accurate but not literal — isomorphic-git's `fetch`/`push` are hard-locked to http(s) transport and cannot target a folder-only remote (see [wayfinder ticket 01](../../.scratch/standalone-storage-sync/issues/01-isomorphic-git-remote-capabilities.md)). The Hidden Clone reaches the Sync Folder via the same hand-rolled object/ref plumbing `androidMirror.ts` already uses today, not the library's high-level fetch/push API. The push/pull semantics this ADR describes are unchanged; only the mechanism is corrected.

**Update (2026-08-22)**: found and fixed a real gap in the hand-rolled plumbing above: `pushObjectsAndRefs()` wrote the shared ref unconditionally (last-write-wins, no compare-and-swap), and `syncNowInternal()` pushed *before* pulling — so a device could overwrite the Sync Folder's ref with its own before ever looking at what another device had put there, orphaning that device's commit (the object survives on disk; nothing points at it anymore). Externally this showed up exactly as this ADR's rejected "silent last-write-wins" option, just reintroduced one layer down: Syncthing observed it as two concurrent edits to the same ref file and produced `.sync-conflict-*` copies instead of merging (there's no textual merge for a git ref); Google Drive's weaker conflict handling on Android showed it as data that "didn't arrive." Fixed by reordering `syncNowInternal()` to pull-and-merge before ever pushing, and giving `pushObjectsAndRefs()` an optional `expectedRemoteRefBytes` compare-and-swap — the ref write is skipped (reported as `conflict: true`, not thrown) if the remote no longer matches what this sync cycle last observed, and the caller retries via another pull+merge (bounded to 3 attempts) rather than clobbering. Covered by new tests in `gitObjectTransport.test.ts`.

**Update (2026-08-22, second finding)**: a related but separate gap, also found while investigating the sync-reliability report above — `remote.listDir()` has no guarantee of returning every entry. Android's Storage Access Framework, specifically Google Drive's `DocumentsProvider` behind it, is known not to reliably enumerate large folders (README's Folder Sync section already recommends Syncthing over it for this reason). A device on such a transport can pull a fraction of the true object set with no error — and `mergeBridge.ts`'s `readEntityJson()` treats a missing object exactly like a legitimate absence (both fail the same `try/catch` the same way), so Structured Merge silently drops changes it never actually saw, rather than erroring. Fixed with `MANIFEST_PATH` (`.git/objects.manifest`): `pushObjectsAndRefs()` now records a monotonic high-water mark of the largest object count any device has ever pushed (never lowered, so one device with a complete view — e.g. Electron's direct filesystem access — permanently raises the floor), and `pullObjectsAndRefs()` reports `complete: false` when its own listing comes in under that floor. `syncNowInternal()` refuses to merge on an incomplete pull, surfacing a clear error through the existing sync-pause banner instead of a silent partial merge. Covered by new tests in `gitObjectTransport.test.ts`.

**Update (2026-08-22, third finding)**: detecting the incomplete-listing case above is only half the fix — a device stuck behind an unreliable SAF listing has no way to make progress, since every retry hits the same enumeration problem. Added `gitBundleTransport.ts` as a fallback: when a pull comes back incomplete, the device now tries downloading and indexing a single git-bundle-format file (`.git/sync.bundle`, real "# v2 git bundle" — genuinely openable via `git bundle verify`/`git clone` outside the app too, built with isomorphic-git's `packObjects`/`indexPack`) instead of enumerating loose objects one by one. `writeBundleIfStale()` keeps this bundle current after a successful push, gated to avoid re-uploading the whole snapshot every cycle (only rewrites once the local object count has grown by a meaningful margin — see its own docstring for the exact thresholds). This does NOT replace the incremental loose-object transport for day-to-day syncing — only the catch-up fallback for the specific case where that transport's own completeness check just failed. Covered by `gitBundleTransport.test.ts` (uses a real temporary git repository, not the in-memory fakes the rest of this suite uses — packing/indexing need genuinely valid git objects, not opaque test bytes).
